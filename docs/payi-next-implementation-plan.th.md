# PAYI — แผนย้ายออเดอร์และเชื่อมเว็บรายคน

จัดทำ 24 กันยายน 2026 จากผลทดลองในเครื่องวันที่ 23 กันยายน 2026 แผนนี้ยังไม่ใช่การอนุมัติสลับระบบจริง

อัปเดตสถานะ v3: ช่วง 1 เสร็จแล้ว เหลือรายการกำกวม 0 แถว ไม่ต้องค้นไฟล์ต้นฉบับเพื่อแก้ 28 แถวอีก สาเหตุคือรหัสถูกแสดงเป็น scientific notation และกู้รหัสเต็มจาก order_key ได้ เทสต์ Python ผ่าน 9/9 งานถัดไปคือ upload session และตัวนำเข้า JS ในเครื่อง ช่วง 2–6 ยังไม่เสร็จ ข้อความตรวจแผนเดิมด้านล่างเก็บเป็นประวัติ

## ตรวจแผนเดิม

แผนเดิมที่ตรวจ: (1) ตรวจ 28 แถวกับไฟล์ marketplace (2) ทำ Import ทดลองที่พักไฟล์ครบก่อนบันทึก (3) เทียบ Dashboard กับ Sheets (4) เชื่อม Turso เมื่อผ่าน OTP แล้วทำ Workspace และเว็บรายคนใช้ข้อมูลร่วมกัน

การประเมิน: ลำดับหลักถูก แต่ยังขาดรายละเอียดก่อนขึ้นออนไลน์ ได้แก่ runtime ของตัวนำเข้า การพักไฟล์ สิทธิ์ผู้ใช้ เจ้าของข้อมูล และการกลับไปใช้ระบบเดิมหลังมีข้อมูลใหม่

การตรวจแยกโดยผู้ช่วยไม่สำเร็จเนื่องจากโควตา จึงใช้การตรวจในงานหลักจากโค้ดและเอกสารที่อ่านจริง ไม่ถือว่าได้รับการรับรองจากผู้ตรวจอิสระ

อ้างอิงเว็บตรวจ 23 กันยายน 2026: [Vercel Hobby](https://vercel.com/docs/plans/hobby), [Turso pricing](https://turso.tech/pricing), [libSQL TypeScript transactions](https://docs.turso.tech/sdk/ts/reference) เอกสาร transaction ระบุ interactive write timeout 5 วินาที จึงต้องวัดการทำงานจริงก่อนใช้กับไฟล์ใหญ่ ห้ามยก transaction ทั้งเดือนจาก Python ไปใช้บนคลาวด์ตรง ๆ

## เป้าหมายและขอบเขต

โมนำเข้าออเดอร์ครั้งเดียว รายงานที่เกี่ยวข้องอ่านข้อมูลชุดเดียวกัน และแต่ละคนเข้าหน้างานตามสิทธิ์ได้ คนเดียวมีหลายหน้าที่ได้โดยไม่ต้องสร้างบัญชีซ้ำตามจำนวนเว็บ

ระยะแรกย้ายเฉพาะข้อมูลออเดอร์และรายงานที่อ่านออเดอร์ คงสูตรยอดขายเดิมเพื่อเทียบผลได้ ไม่ย้ายทุกชีท ไม่สร้าง Finance ใหม่ ไม่เริ่ม CRM ที่ยังไม่มีคน และไม่เปลี่ยนระบบ Live/Floor ทั้งชุดพร้อมกัน งานเหล่านี้ยังอยู่ในแผนระยะต่อไป

## แบบของตัวนำเข้า

ใช้ JavaScript ฝั่ง API ให้เข้ากับเว็บเดิม พร้อม storage adapter สำหรับ SQLite/libSQL รุ่นไลบรารีต้องตรวจความเข้ากันได้และล็อกใน lockfile เมื่อเริ่มลงมือ ไม่เพิ่มทั้ง Python service และ Node service สำหรับงานเดียวกัน ชุด Python ปัจจุบันเป็นตัวเทียบผลทดสอบ

ข้อมูลข้ามขอบเขตที่ต้องมี:

- `upload`: id, uploader_id, platform, business, file_hash, expected_chunks, expected_rows, parser_version, status
- `chunk`: upload_id, chunk_index, content_hash, row_count; คีย์ upload_id + chunk_index ต้องซ้ำไม่ได้ ถ้าส่งซ้ำเนื้อหาตรงให้ตอบรับเดิม ถ้าไม่ตรงให้หยุด
- `review`: upload_id, source_row, reason, resolution, reviewer_id, resolved_at
- `order_line`: id ถาวร, business, platform, order_id, native_item_id ถ้ามี, legacy_key, source_ref และข้อมูลสินค้า/ยอด/สถานะ
- `import_batch`: id, upload_id, status, counts, created_by, created_at, published_version

สถานะหน้าจอ: กำลังรับไฟล์ → ตรวจครบไฟล์ → มีรายการรอตรวจ/พร้อมนำเข้า → กำลังบันทึก → สำเร็จหรือผิดพลาด แสดงจำนวนรับครบแล้ว จำนวนเพิ่ม/อัปเดต/ไม่เปลี่ยน และรายการที่ต้องตรวจ ผู้ใช้กลับเข้าหน้าเดิมแล้วเห็นสถานะล็อตเดิมได้

พักข้อมูลก่อนเผยแพร่: chunks บันทึกได้โดยยังไม่เปลี่ยนยอดจริง เมื่อครบและตรวจผ่านจึงเผยแพร่ผล หากไฟล์ใหญ่เกินเวลา transaction ให้เขียนข้อมูลเป็นรุ่นที่ยังไม่ active แล้วสลับตัวชี้รุ่นด้วย transaction สั้นพร้อมตรวจรุ่นก่อนหน้า ทุก reader ต้องกรองเฉพาะรุ่น active วิธีนี้ต้องมี integration test เมื่อทดสอบบน libSQL จริง ไม่ถือว่าโค้ด Python ปัจจุบันรองรับแล้ว

ไฟล์กำกวมทั้งไฟล์ยังไม่เผยแพร่ ผู้ตรวจเลือกผูกกับรายการเดิมหรือเพิ่มรายการใหม่โดยมีหลักฐาน ห้ามใช้ยอด สถานะ หรือเลขชุดอัปโหลดเป็นรหัสรายการ ประวัติต้องเก็บก่อน/หลังแก้และผู้ทำ

## ใครเป็นเจ้าของข้อมูล และเว็บแต่ละคนอ่านอย่างไร

ให้ส่วนออเดอร์ของ Ops เป็นผู้เขียนออเดอร์กลางเพียงแห่งเดียว เว็บ CEO/CMO/Finance อ่านผ่าน API ตามสิทธิ์ ระบบ Floor เป็นเจ้าของงานแพ็ค/คน และ Management เป็นเจ้าของรอบไลฟ์ การเชื่อมภายหลังใช้รหัสอ้างอิง ไม่คัดลอกออเดอร์ไปแก้หลายฐาน

คำว่าใช้ข้อมูลเดียวกันไม่จำเป็นต้องย้ายทุกระบบเข้าฐานเดียววันนี้ Live ใช้ฐานเดิมได้ ส่วนฐานออเดอร์แยกวงทดลองก่อน หาก backend/core ต้องใช้ยอดออเดอร์ให้เป็นผู้อ่านจนกว่าจะมีแผนย้ายเจ้าของข้อมูลชัดเจน

บัญชีร่วมต้องมี user ID เดียวและหลายสิทธิ์ เช่น orders.import, orders.review, reports.read, live.manage, affiliate.manage, floor.manage, finance.read ทุก API ตรวจสิทธิ์ การซ่อนเมนูอย่างเดียวไม่เพียงพอ ห้ามส่ง database token ไปเบราว์เซอร์

Workspace เริ่มจากเมนูและงานของฉันตามสิทธิ์ ภายหลังจึงเชื่อมการเข้าสู่ระบบร่วมข้ามเว็บอย่างเป็นระบบ ไม่ถือว่าลิงก์เมนูทำให้ login ครั้งเดียวได้ทันที การเลือก auth provider/session และโฮสต์เป็นจุดตัดสินใจในช่วง 4 ก่อนลงมือ SSO

| ผู้ใช้ / หน้างาน | งานเริ่มต้น | หมวดข้อมูล |
|---|---|---|
| โม | Import ตรวจข้อมูล Dashboard ระบบ/เว็บไซต์ และยิง CPAS ตามโปรโมชั่นที่ได้รับ | Ops/CEO/CMO ตามสิทธิ์ |
| ตูน | สินค้าใหม่ พัฒนาสินค้าเดิม Segment AOV Branding และแผนการตลาด | CMO |

| แตง | แพ็ค สต็อก คนฟีด พาร์ทไทม์ และงานหน้างาน | Floor |

## ฟรี 100% และกำลังรองรับ

## การย้อนระบบ

ก่อนสลับ: snapshot ชีท + backup ฐาน + รุ่นแอป + เวลา cutoff และรายการล็อตที่นำเข้าแล้ว ต้องกู้คืนในฐานแยกและตรวจยอดได้

ระหว่างสลับ: หยุดนำเข้าชั่วคราว ดึงข้อมูลตกค้าง ตรวจยอด แล้วเปิดผู้เขียนใหม่เพียงทางเดียว

หลังสลับ: เก็บ ledger ของการเพิ่ม/แก้/ย้อนล็อตทุกครั้งตั้งแต่ cutoff ถ้าต้องกลับไป Sheets ต้องหยุดเขียน ส่งออกผลเปลี่ยนแปลง ตรวจ replay ในสำเนาชีทแล้วเทียบยอดก่อนคืนระบบ ห้ามสลับกลับไปใช้ชีทเก่าทันทีจนข้อมูลใหม่หาย การ undo ล็อตล่าสุดในตัวทดลองไม่ได้แทนขั้นตอนนี้

## งานชุดแรกที่ลงมือได้ทันที

1. เก็บ commit งานทดลอง v3 และเอกสาร โดยไม่รวมข้อมูลจริงและ secrets
2. ทำ upload session / chunk / finalize แบบถาวรในฐานทดลอง พร้อมตรวจผู้เป็นเจ้าของ session
3. ทำตัวนำเข้า JS จาก normalized rows เทียบผล v3 ก่อนเชื่อม parser ของแต่ละแพลตฟอร์ม
4. จากนั้นทำหน้า Import ทดลองของโมให้จบหนึ่งเส้นทาง: เลือกไฟล์ → ตรวจ → แก้รายการกำกวม → นำเข้า → เห็นยอดเทียบ

ยังไม่มีคำถามที่ต้องให้โมตัดสินใจก่อนเริ่มชุดนี้ ก่อนเปิดออนไลน์ต้องตัดสินใจโฮสต์และการเข้าถึงจากนอกสถานที่จากตัวเลือกที่ตรวจแล้ว

สิ่งที่เพิ่มจากแผนเดิม: เกณฑ์ผ่านแต่ละช่วง สัญญาการอัปโหลดครบไฟล์ เจ้าของข้อมูลและสิทธิ์ การประเมินโฮสต์ฟรี และวิธีย้อนระบบหลังมีข้อมูลใหม่
