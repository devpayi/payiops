# PAYI: โครงสร้างสำหรับผู้พัฒนาคนเดียว

วันที่ 22 กันยายน 2026 — ข้อเสนอปรับจากแผน 7 พื้นที่ทำงาน ยังไม่ได้เปลี่ยนระบบจริง

## เงื่อนไขเพิ่มเติม: ฟรี 100% และเพดาน 12 Functions

ผู้ใช้ยืนยันว่าข้อจำกัดคือ 12 Functions/API ต่อโปรเจกต์ Vercel ไม่ใช่จำนวนผู้ใช้ ส่วนนี้ปรับข้อเสนอด้าน deployment ด้านล่าง: อนุญาตแยกแอปและ deployment ตามฝ่าย โดยใช้โค้ดส่วนร่วมและกติกาข้อมูลชุดเดียว การมีระบบกลางในเชิงโค้ดไม่ได้บังคับให้ deploy ทุกอย่างในโปรเจกต์เดียว

โครงสร้างเริ่มต้นที่เสนอคือ CEO, Growth (รวม Content/CRM), Floor, Live และ Finance รวม 5 deployment ส่วน Content/CRM แยกเพิ่มเมื่อมีเหตุด้านการใช้งานหรือขนาดจริง หากของเดิมแยกอยู่แล้วให้รักษาไว้ก่อน ไม่ย้ายเพียงให้ตรงผัง

กำหนดงบออกแบบ 6–8 Functions ต่อ deployment เพื่อเผื่อที่สำหรับงานใหม่ ตัวเลขนี้เป็นเพดานภายในที่เสนอ ไม่ใช่จำนวนจากผล build การจัด router ให้หนึ่ง Function รับหลาย operation ทำได้ตามรูปแบบที่โค้ด api/marketing.js และ api/sheet-tools.js ใช้อยู่แล้ว แต่ยังต้องตรวจสิทธิ์ราย operation และทดสอบผล build จริง

ตรวจครั้งนี้พบไฟล์ JS ระดับบนใน api จำนวน 10 ไฟล์ ตัวเลขนี้ไม่ใช่การยืนยันจำนวน Functions ที่ Vercel deploy จริง ต้องตรวจ build output รวมทั้งสิ่งที่ framework สร้างด้วย

ข้อจำกัดโฮสต์ที่ยังต้องตัดสินใจ: [Vercel Hobby](https://vercel.com/docs/plans/hobby) ระบุการใช้งานส่วนบุคคลที่ไม่ใช่เชิงพาณิชย์ (ตรวจ 22 กันยายน 2026) จึงยังรับรองแผนให้ระบบธุรกิจ PAYI ใช้ Hobby ฟรีทั้งหมดไม่ได้ การแยกโปรเจกต์ไม่ได้แก้เงื่อนไขประเภทการใช้งาน และไม่ได้รับรองว่าโควตารวมบัญชีจะเพิ่มตามจำนวนโปรเจกต์ ต้องเลือกโฮสต์ฟรีที่รองรับลักษณะงานและปริมาณจริง หรือประเมินเครื่องเดิมที่บริษัทมี โดยแยกค่าโฮสต์ออกจากต้นทุนไฟ อินเทอร์เน็ตและการดูแล

ยังไม่เปลี่ยนโฮสต์ ย้ายข้อมูล หรือแยก deployment จริงในขั้นนี้

## เป้าหมาย

คุณพัฒนาและดูแลระบบทั้งหมดได้ โดยแต่ละฝ่ายรับผิดชอบข้อมูลและขั้นตอนงานของตัวเอง ระบบต้องช่วยให้เห็นงานที่ขัดขวางยอดขาย 150 ล้านบาทและส่งงานต่อได้จริง ตัวเลข 150 ล้านบาทเป็นเป้าธุรกิจ ไม่ใช่หลักฐานว่าจำเป็นต้องมีเว็บหรือฐานข้อมูล 7 ชุด

ภาพการใช้งานที่ต้องทำให้สำเร็จ: ผู้รับผิดชอบ Growth สร้างแคมเปญและเลือกสินค้า ส่งบรีฟให้ Content ผู้ทำ Live เห็นสื่อที่อนุมัติและสินค้าพร้อมขาย Floor เห็นวันเริ่มแคมเปญเพื่อเตรียมสินค้า CEO เห็นงานติดขัดพร้อมชื่อผู้รับผิดชอบ ทุกฝ่ายอ้าง campaign_id เดียวกัน คุณไม่ต้องคัดลอกข้อมูลให้แต่ละฝ่าย

## ทบทวนแผนเดิม

ขอบเขตเดิม: CEO ดูเป้าและตัดสินใจ; Growth ดูแคมเปญ Ads Affiliate B2B; Content ผลิตและอนุมัติสื่อ; CRM ติดตามและซื้อซ้ำ; Floor ดูคน สินค้า แพ็ค ส่ง; Management ดู Live; Finance ดูเงิน ต้นทุนและกระทบยอด แผนเดิมเสนอใช้ข้อมูลร่วมและต่อยอด Floor/Management

สิ่งที่เก็บไว้คือการแบ่งหน้าที่และการใช้ของเดิม สิ่งที่เพิ่มคือผู้รับผิดชอบข้อมูล แผนย้ายระบบทีละส่วน และคิวพัฒนาร่วม เพราะแผนรายชื่อแอปอย่างเดียวยังไม่ช่วยผู้พัฒนาคนเดียวตัดสินใจว่าจะสร้างอะไรพรุ่งนี้

หลักฐานในโค้ดที่อ่านครั้งนี้:

- shared/roles.js มีบทบาทและสิทธิ์ Marketing, Finance, Stock อยู่แล้ว
- src/App.jsx:31–33 และ 128–148 มี Marketing Radar, Content OS Prototype และ CFO อยู่แล้ว จึงต้องตรวจใช้ซ้ำก่อนสร้างใหม่
- src/App.jsx:1463 ยังเปิด CFO เฉพาะ isDev แม้ shared/roles.js ให้บทบาท Finance เห็นแท็บ ต้องตรวจทั้งเส้นทางใช้งานก่อนสรุปว่าฝ่ายการเงินใช้ได้
- backend/core/README.md:5–15 ระบุ Core อีกชุดบน Next.js/Express/PostgreSQL และระบุว่ายังไม่ได้ย้าย Sheets เข้า PostgreSQL
- backend/core/apps/api/src/app.ts:30–35 มี auth, operations, settings, procurement และ permission ฝั่ง API เป็นจุดตั้งต้น ไม่ควรสร้าง Core ใหม่ซ้อน
- backend/core/integration/mona-bridge.ts:33,42,53 จำกัด bridge ที่ GET, สิทธิ์ dev และมุมกำไร จึงยังถือว่าไม่ได้เชื่อมข้อมูลและบัญชีทั้งระบบเข้าด้วยกัน

ผลตรวจแผนแบบแยกบริบท: พบประเด็นสำคัญ 3 ข้อ ได้แก่ ต้องใช้ Core เดิมเป็นฐานประเมิน ต้องระบุผู้เขียนข้อมูลหลักก่อนเชื่อม และต้องเทียบสิทธิ์เว็บเดิมกับสิทธิ์ Core โดยตรง ทั้งสามข้อถูกใส่ในลำดับงานด้านล่างแล้ว

ข้อจำกัด: ยังไม่ได้ตรวจโค้ดหรือระบบที่เปิดใช้งานจริงของ Floor และ Management จึงไม่กำหนดให้ย้ายหรือรวมทันที ไม่ได้ทดสอบความพร้อม production ของ Core ในการจัดทำแผนครั้งนี้

## โครงสร้างที่เสนอ

PAYI เป็นชื่อระบบรวม มีทางเข้าตามหน้าที่ 7 พื้นที่ และ Dev Hub สำหรับคุณเท่านั้น ระยะแรกใช้เว็บหลักเดิมและลิงก์ไป Floor/Management ที่ยังทำงานแยกอยู่ การมีลิงก์รวมยังไม่ถือว่ามี Single Sign-On

| พื้นที่ | หน้าที่และหน้าเริ่มต้น | ขอบเขตแรก |
|---|---|---|
| CEO | เป้าเทียบยอดจริง งานติดขัด การตัดสินใจ | อ่านข้อมูลรวมและตัดสินใจ ไม่กรอกยอดซ้ำ |
| Growth | แคมเปญช่องทางขาย Ads Affiliate B2B | แคมเปญที่กำลังทำพร้อมเป้า เจ้าของ และวันจบ |
| Content | งานวันนี้ บรีฟ ตรวจงาน สื่อพร้อมใช้ | งานผูกแคมเปญพร้อมผู้อนุมัติและเวอร์ชันสื่อ |
| CRM | งานติดตามวันนี้ ประวัติติดต่อ โอกาสขาย | เจ้าของลูกค้า นัดครั้งถัดไป และผลติดตาม |
| Floor | งานแพ็คค้าง สต็อกติดขัด งานส่ง | ต่อระบบเดิมหลังตรวจแหล่งข้อมูลจริง |
| Management / Live | รอบวันนี้ สินค้า สื่อและผลต่อรอบ | ต่อระบบเดิมและอ้างแคมเปญกลาง |
| Finance | เงินค้างรับ ยอดต่างและรายการต้องตรวจ | ใช้ยอดออเดอร์ต้นทางร่วม แยกเงินรับจริง |

Content และ CRM เริ่มเป็นโมดูลในเว็บเดียวกับ Growth ได้ แต่แยกสิทธิ์และลิงก์เข้าหน้าของตัวเอง ผู้ทำ Content ไม่จำเป็นต้องเห็นข้อมูลลูกค้า CRM

## หลักสถาปัตยกรรม

ใช้การแยกโมดูลในระบบที่ดูแลร่วมกัน ก่อนเพิ่มบริการที่ต้อง deploy แยก ทีมที่มีนักพัฒนาคนเดียวต้องรับต้นทุนการปล่อยระบบ การเฝ้าดู และการกู้คืนทุกบริการเอง แนวทางนี้สอดคล้องกับข้อพิจารณาใน [Monolith First, 3 มิถุนายน 2015](https://martinfowler.com/bliki/MonolithFirst.html) และการแบ่งส่วนภายในแอปใน [Microsoft: Common web application architectures](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures) อ่านแหล่งข้อมูลเมื่อ 22 กันยายน 2026 เป็นหลักออกแบบ ไม่ใช่คำแนะนำให้เปลี่ยนมาใช้ .NET

1. รักษา Dashboard เดิมสำหรับงานที่กำลังใช้ ตรวจ Core ที่มีอยู่ก่อนตัดสินใจให้เป็น backend หลักของโมดูลใหม่
2. แยกโมดูลตามงานธุรกิจ: sales, campaigns, content, crm, inventory, live, finance ส่วน CEO เป็นมุมมองรวม
3. ใช้กลไกตรวจสิทธิ์ร่วม ฝั่ง API ต้องตรวจทุกการอ่าน/เขียนที่มีข้อจำกัด การซ่อนเมนูอย่างเดียวไม่พอ
4. ใช้สินค้า ออเดอร์ และตัวตนลูกค้าตามรหัสกลาง โดยมีตารางเทียบรหัสจากแหล่งเดิม
5. เก็บเวอร์ชันข้อมูลและประวัติผู้แก้ รายการแหล่งข้อมูลที่ซิงก์สำเร็จล่าสุด และข้อผิดพลาดที่ต้องแก้
6. ยังไม่ย้ายโฟลเดอร์หรือเปลี่ยน framework ทั้งระบบ งานจัดโครงสร้างต้องไม่หยุดงานแพ็คหรือขาย

โครงสร้างโค้ดเป้าหมายเชิงแนวคิด: UI แต่ละโมดูลเรียก API ของโมดูลนั้น; โมดูลใช้ auth, permissions, audit และการเข้าถึงฐานข้อมูลร่วม ส่วน connectors รับข้อมูล Sheets/Marketplace/ระบบเดิมเข้าจุดเดียว การจัดชื่อโฟลเดอร์จริงต้องอิง Core ปัจจุบันหลังตรวจครบ

## ข้อมูลใครเป็นเจ้าของ

| ข้อมูล | ผู้รับผิดชอบความถูกต้องทางธุรกิจ | กติกาเขียน |
|---|---|---|
| สินค้าและ SKU | ผู้ดูแลสินค้า/สต็อกที่มอบหมาย | แหล่งหลักเดียว มีรหัสเทียบแต่ละช่องทาง |
| ออเดอร์และสถานะขาย | ผู้ดูแลการนำเข้ายอดขาย | นำเข้าผ่านช่องทางเดียว ตรวจรหัสซ้ำ |
| แคมเปญและเป้าช่องทาง | Growth | ฝ่ายอื่นอ้างรหัสแคมเปญ |
| สื่อและการอนุมัติ | Content | เก็บเวอร์ชันและผู้อนุมัติ |
| ลูกค้าและงานติดตาม | CRM | จับคู่ลูกค้าด้วยกติกาที่ตรวจสอบได้ |
| สต็อกและการเคลื่อนไหว | Floor | บันทึกผ่านโมดูลคลัง ห้ามแก้จำนวนจาก Growth |
| รอบ Live และผลปฏิบัติงาน | ผู้ดูแล Live | รอบมีรหัสของตัวเอง เชื่อมสื่อ/แคมเปญ |
| รับเงิน ค่าธรรมเนียม กระทบยอด | Finance | อ้างออเดอร์เดิม เพิ่มรายการการเงินแยก |

ตำแหน่งเหล่านี้ไม่จำเป็นต้องเป็นคนละคน แต่ทุกชุดข้อมูลต้องระบุชื่อคนรับผิดชอบก่อนเริ่มใช้ คุณรับผิดชอบความถูกต้องของระบบ เจ้าของงานรับผิดชอบการกรอก ตรวจ และรับรองข้อมูลธุรกิจ

ระหว่างย้ายระบบให้ระบุ source of truth รายชุดข้อมูลอย่างชัดเจน เช่น ออเดอร์ย้อนหลังยังอ่านจาก Sheets ส่วนแคมเปญใหม่เขียนใน Core ที่ผ่านการตรวจ ห้ามเปิดให้สองระบบแก้รายการเดียวกันโดยไม่มีกติกาแก้ความขัดแย้ง

ข้อมูลข้ามโมดูลขั้นต่ำที่เสนอ:

```text
Campaign: id, company_id, name, channel, owner_id, target_amount,
          start_date, end_date, status, version
Task: id, company_id, campaign_id, workspace, assignee_id,
      due_at, status, blocked_reason, updated_at, version
SourceMap: company_id, source_system, entity_type, external_id, internal_id
ImportRun: id, source_system, started_at, completed_at,
           accepted_count, rejected_count, status, error_reference
```

นี่เป็นสัญญาข้อมูลที่เสนอ ต้องเทียบ schema เดิมก่อนเพิ่มตาราง เงินใช้ decimal หรือหน่วยสตางค์ตามวิธีที่ Core ใช้อยู่ รายการนำเข้าใช้คีย์ source + company + external_id เพื่อป้องกันซ้ำ การบันทึกจากหน้าที่มี version เก่าต้องแจ้งให้โหลดข้อมูลล่าสุดก่อนแก้ต่อ

## หน้าควบคุมสำหรับคุณ

ต่อยอด Dev Hub เดิมเป็นพื้นที่ตรวจระบบ จำกัดเฉพาะผู้ดูแล มี 4 มุมมองที่จำเป็น:

- แผนที่ระบบ: URL, repo/โฟลเดอร์, สภาพแวดล้อม, เวอร์ชันที่ deploy, ผู้ใช้งาน, แหล่งข้อมูล และวิธีย้อนกลับ
- สุขภาพข้อมูล: ซิงก์สำเร็จล่าสุด จำนวนรายการผิดพลาด ข้อมูลซ้ำ และการสำรองครั้งล่าสุด
- คิวพัฒนาเดียว: ข้อผิดพลาด งานปรับปรุง โมดูล ผลต่อธุรกิจ ผู้รับรองงาน และสถานะ
- บันทึกปล่อยระบบ: เปลี่ยนอะไร ทดสอบอะไร วิธีปิด feature และผู้ตรวจรับ

เริ่มรายการเหล่านี้เป็นเอกสารหรือบอร์ดธรรมดาก่อนได้ ค่อยทำเป็นหน้าจอเมื่อใช้ซ้ำบ่อย ห้ามเก็บรหัสผ่านหรือ API secret ในบอร์ด

## วิธีรับงานและแบ่งเวลาของผู้พัฒนาคนเดียว

ทุกคำขอใช้ข้อมูลชุดเดียว: ใครใช้ / ติดขัดตรงไหน / ตัวอย่างจริง / ต้องการให้เกิดอะไร / ผลต่อยอดขายหรือเวลาทำงาน / ต้องใช้เมื่อใด / ใครตรวจรับ

ลำดับคิว: เหตุที่ทำให้ขายหรือส่งไม่ได้และข้อมูลเสีย → งานปลดคอขวดรายได้ → งานลดงานมือซ้ำ → งานตกแต่งที่ยังไม่กระทบการใช้งาน โดยพิจารณาจำนวนผู้ใช้และเวลาทำจริงด้วย

ให้มีงานพัฒนาหลักที่กำลังทำเพียงหนึ่งงาน และช่องแก้เหตุเร่งด่วนหนึ่งช่อง หากมีเหตุใหม่เข้ามาต้องระบุว่างานเดิมเลื่อนอะไร แนะนำกรอบเริ่มต้น 60% พัฒนางานเพิ่มรายได้ 25% แก้ปัญหาและข้อมูล 15% ทดสอบ คู่มือและสำรอง เป็นการจัดเวลาเสนอ ไม่ใช่เปอร์เซ็นต์ที่พิสูจน์จากผลงานของคุณ

กำหนดเวลาทบทวนคิวสัปดาห์ละครั้งร่วมกับเจ้าของงาน ให้แต่ละฝ่ายเสนอผู้รับรองแทนการให้คุณตัดสินใจรายละเอียดธุรกิจทั้งหมด

## ลำดับลงมือและเกณฑ์ผ่าน

| ชุดงาน | สิ่งที่ส่งมอบ | หลักฐานว่าจบ |
|---|---|---|
| 0 สำรวจของจริง | รายการ Dashboard/Core/Floor/Management และผู้เขียนข้อมูลแต่ละชนิด | ทราบ URL/repo/ฐานข้อมูล/สิทธิ์/สำรอง/ผู้ใช้ และช่องที่ยังไม่รู้ |
| 1 จัดทางเข้าและสิทธิ์ | เมนูตามงาน ลิงก์ระบบเดิม นิยามยอดขายร่วม | บัญชีตัวแทนแต่ละฝ่ายทำงานได้ และเรียก API เกินสิทธิ์ไม่ได้ |
| 2 แคมเปญหนึ่งงานครบทาง | Growth สร้างแคมเปญ Content รับบรีฟ Live ใช้สื่อ | ส่งงานจริงครบเส้นทาง ไม่ต้องให้คุณคัดลอกข้อมูลให้ |
| 3 ต่อข้อจำกัดการส่งของ | แคมเปญอ้างสถานะสินค้าจาก Floor | บอกสินค้าไม่พร้อมก่อนเริ่มขาย และเห็นเวลาข้อมูลล่าสุด |
| 4 CRM ติดตามยอด | งานติดตามพร้อมผลและออเดอร์อ้างอิง | ผู้รับผิดชอบเห็นงานวันนี้ และการซื้อซ้ำไม่นับยอดเพิ่มซ้ำ |
| 5 Finance และการย้ายทีละส่วน | คิวตรวจยอดต่างและยอดรับจริง | ตัวอย่างออเดอร์ตรวจกลับต้นทางได้ อธิบายส่วนต่างได้ |

ไม่รับปากระยะเวลารวมก่อนสำรวจ Floor/Management และเวลาที่คุณมีต่อสัปดาห์ แบ่งแต่ละชุดเป็นงานย่อยที่ส่งให้ผู้ใช้ทดลองได้ และประเมินใหม่จากเวลาที่ทำชุดแรกจริง

## คุณภาพที่ต้องเห็นบนหน้าจอ

- หน้าแรกแต่ละฝ่ายเปิดที่งานวันนี้ พร้อมผู้รับผิดชอบ วันครบกำหนด และปุ่มไปทำงาน
- งานติดขัดต้องมีเหตุผลและคนที่รอ ห้ามแสดงเพียงสีแดงโดยไม่บอกการแก้
- ไม่มีข้อมูลให้แสดงว่า “ยังไม่มีข้อมูล” และแนะนำขั้นตอนแรก ไม่แสดงเป็นยอดศูนย์ที่ยืนยันแล้ว
- ซิงก์ล้มเหลวให้เก็บข้อมูลสำเร็จล่าสุดพร้อมเวลาข้อมูลและสถานะล้าสมัย
- สื่อที่ถูกตีกลับต้องบอกเหตุผลและเวอร์ชันที่ต้องแก้
- ผู้ใช้กลับมาครั้งถัดไปเห็นงานที่มอบหมายใหม่และงานค้างของตน
- แสดงแยกยอดสั่งซื้อ ยอดขายตามนิยามรายงาน และเงินรับจริง ระบุช่วงเวลาและวันอ้างอิง
- ออเดอร์หนึ่งรายการมีเจ้าของยอดขายหลักหนึ่งช่องทาง ส่วนแคมเปญ/Content/Live/CRM เป็นมุมวิเคราะห์ ไม่บวกยอดเข้าบริษัทซ้ำ

## ปล่อยระบบและย้อนกลับ

ใช้ข้อมูลทดสอบและสิทธิ์ทดสอบแยกจากงานจริง สำรองก่อนเปลี่ยน schema และลองกู้คืนในพื้นที่แยก สำหรับการย้ายข้อมูลให้เทียบจำนวนรายการ ผลรวมและตัวอย่างรายการก่อนเปลี่ยนผู้เขียนหลัก หยุดเขียนที่ระบบเดิมของชุดข้อมูลนั้นก่อนเปิดระบบใหม่

เปิดฟีเจอร์กับผู้ใช้ตัวแทนก่อน และเตรียมปิดกลับไปมุมมองเดิมได้ หากมีรายการใหม่เกิดหลังสลับระบบ ต้องส่งออกและกระทบยอดก่อนย้อนกลับ ห้ามกู้ backup ทับฐานที่มีรายการใหม่โดยตรง เก็บตาราง/ฟิลด์เดิมระหว่างตรวจรับแล้วค่อยวางแผนเลิกใช้

## การเปลี่ยนจากแผนเดิม

- เพิ่มข้อจำกัดผู้พัฒนาคนเดียวเป็นหลักในการจัดคิวและกำหนดจำนวนส่วนที่ต้องดูแล
- ใช้ Core ที่พบในโค้ดเป็นจุดประเมินก่อนเริ่ม ไม่สร้างระบบกลางอีกชุด
- ให้ 7 พื้นที่เป็นการแบ่งงานและสิทธิ์ การแยก deployment ต้องมีเหตุจากการใช้งานจริง
- เพิ่มเจ้าของข้อมูลและผู้ตรวจรับ เพื่อไม่ให้นักพัฒนากลายเป็นผู้กรอกและอนุมัติข้อมูลทุกฝ่าย
- เริ่มด้วยแคมเปญหนึ่งเส้นทางที่ใช้ได้ครบ ก่อนขยายฟีเจอร์ทั้งเจ็ดด้าน

ข้อมูลที่ยังต้องสำรวจ: ตำแหน่งและสถานะใช้งานจริงของ Floor/Management, ผู้ตรวจรับแต่ละฝ่าย, จำนวนผู้ใช้พร้อมกันและชั่วโมงพัฒนาต่อสัปดาห์ ข้อมูลเหล่านี้ใช้กำหนดตารางส่งมอบและจุดเชื่อมจริง ไม่ขัดขวางการเริ่มทำบัญชีระบบและคิวงานกลาง
