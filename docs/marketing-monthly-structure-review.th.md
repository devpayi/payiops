# ทบทวนโครงสร้างรายงานรายเดือนก่อนเปลี่ยนหน้า

วันที่ตรวจ: 16 ตุลาคม 2569 — อ่านโค้ดและให้ผู้ตรวจอีกบริบทตรวจอย่างอิสระ ผู้ตรวจไม่แก้ไฟล์

## ข้อเสนอที่นำมาตรวจ (ตรึงขอบเขต)

ใช้ Ads & Channels เดิม เปลี่ยนชื่อเป็น “วิเคราะห์โฆษณา” มีภาพรวมรายเดือน รายสินค้า และรายแคมเปญ ย้ายยอดขาย Affiliate/Live/Video และฟอร์มเดิมไปแท็บ “ช่องทางขาย TikTok” ใต้ Dashboard สรุปยอดขาย ตั้งราคาและกำไรคงอยู่แยกและรักษาสิทธิ์ dev/boss รายงาน CSV ใหม่ใช้เดือนปฏิทินและอาจเชื่อมข้อมูลตั้งราคาในภายหลัง ยังไม่ทำ API แพลตฟอร์ม ไม่แก้เงินจริง และยังไม่ push

แผนตั้งต้นยังขาดรายละเอียดเรื่องการเขียนทับข้อมูล นิยามยอดขาย และการตัดสินใจว่าจะใช้ยอดค่าแอดชุดใดกับ Dashboard/CFO การย้ายหน้าตามข้อเสนอทันทีจึงยังไม่พร้อม

## ด้านที่ตรวจ

- ขอบเขตข้อมูลและการบันทึก: ต้องกันการแก้ฝั่งหนึ่งลบอีกฝั่ง รวมถึงการบันทึกพร้อมกันบน serverless
- ความหมายและการรวมยอด: ต้องแยกภาษี มิติ TikTok และระดับ subtotal/member ก่อนแสดงตัวเลขรวม
- สิทธิ์และพฤติกรรมหน้า React: การย้ายเข้า Dashboard ต้องไม่เปิดสิทธิ์มากขึ้น และฟอร์มค้างต้องไม่ทำให้เดือน/ยอดผิด
- การย้ายและย้อนกลับ: ต้องกลับหน้าเดิมได้โดยไม่สูญเสียข้อมูลใหม่หรือเปลี่ยน KPI ที่ผู้ใช้กำลังอ้างอิง

## สิ่งที่แผนเดิมเหมาะสมแล้ว

การแยกยอดขายออกจากค่าโฆษณาสอดคล้องกับงานของบอส ใช้เมนูเดิมช่วยลดเมนูซ้ำ เดือนปฏิทินทำให้เทียบสองแพลตฟอร์มได้ การรักษาหน้าตั้งราคาและสิทธิ์เดิมช่วยจำกัดขอบเขตการเปลี่ยน

## แผนที่ปรับแล้ว

รายละเอียดที่ใช้พัฒนาต่ออยู่ใน [แผนโครงสร้าง](marketing-monthly-structure-plan.th.md) โดยลำดับงานคือ:

1. เก็บ baseline และข้อมูลตัวอย่างสำหรับตรวจยอด/สิทธิ์ก่อนแก้ runtime
2. แยกส่วนอ่านและแสดงผลโดยปิด feature ไว้ และคง legacy writers/consumers ไว้เดิม
3. ทำรายงาน Shopee กันยายนเป็น preview ที่ตรวจยอดและป้องกันนำเข้าซ้ำได้ ข้อมูลดิบอยู่ต่างหาก
4. เปิดแท็บยอดขาย TikTok แบบอ่านอย่างเดียวและชื่อเมนูใหม่หลังตรวจหน้าเว็บจริง
5. ย้ายฟอร์มเมื่อ writer ใหม่ผ่าน scoped updates, concurrency, stale conflict และ timeout recovery; ถอน full-month write ในขั้นเดียวกัน
6. การเลือกยอดรายงานแทนค่าแอดทางการของ Dashboard/CFO เป็นการเปลี่ยนแยก ต้องตกลง basis และเทียบยอดก่อน

ขั้นตอนการอ่านรายงานไม่ใช่การอนุมัติให้นำค่าใหม่ไปแทนค่าทางการ รายงานที่ยังไม่มีข้อมูลต้องแสดง missing ไม่แสดง 0 หรือยอดประมาณที่ดูเหมือนจริง

## เงื่อนไขตรวจที่เพิ่มจากแผนตั้งต้น

- บันทึก Ads → TikTok → Ads แล้ว domain อื่น ธุรกิจอื่น เดือนอื่นไม่เปลี่ยน
- สอง client ใช้ revision เก่าหรือบันทึกต่างเดือนพร้อมกันไม่ทำลายข้อมูล; unknown result ตรวจกลับได้โดยไม่บันทึกซ้ำ
- source ต้นฉบับ, subtotal/member, ไฟล์ซ้ำ, revised file, เดือนสั้น/ปีอธิกสุรทิน, VAT unknown, สินค้ายังไม่จับคู่มีผลทดสอบชัดเจน
- ค่า Dashboard/Monthly/CFO ก่อนและหลัง import/navigation ต้องเหมือนเดิมจนกว่าจะมีการเปลี่ยนแหล่งทางการ
- ทดสอบ role staff/marketing/boss/dev ทั้งการคลิกและยิง API โดยตรง สิทธิ์ตั้งราคาไม่เปลี่ยน
- เมื่อย้อนกลับ ปิด feature ได้โดยคง raw source และ revisions; ก่อน restore ต้องตรวจ intervening writes และหยุด writer

## แหล่งข้อมูลภายนอกที่ใช้ตรวจ

- TikTok Thailand, [GMV refinement](https://seller-th.tiktok.com/university/essay?knowledge_id=4862402286487297), เผยแพร่ 28 พ.ค. 2026 ตรวจ 16 ต.ค. 2026: ระบุ order source Affiliate/Seller และ content type LIVE/short video/Product Card แยกกัน มี direct/indirect และนิยามย้อนหลังอาจเปลี่ยน จึงไม่แปลงยอดเดิมโดยเดา
- React, [Sharing State Between Components](https://react.dev/learn/sharing-state-between-components) และ [Preserving and Resetting State](https://react.dev/learn/preserving-and-resetting-state), ตรวจ 16 ต.ค. 2026: ใช้หลักเจ้าของ state เดียวและกำหนดความต่อเนื่อง/การ reset ของฟอร์ม ไม่ต้องเพิ่ม global store สำหรับงานนี้

## ข้อที่ยังต้องยืนยัน

TikTok ยังรอการเข้าบัญชีเพื่อดูไฟล์จริง ฐานภาษีของรายงานแต่ละประเภทและ mapping item ID ต้องตรวจหลักฐานก่อนเปิดใช้ การเลือกรายงานนำเข้าเป็นยอดค่าแอดทางการต้องให้เจ้าของเห็นผลเทียบก่อน ทุกข้อเหล่านี้ไม่ขวางการจัดทำแผนหรือทำ read-only prototype ในภายหลัง แต่ขวางการเปิด writer/เปลี่ยนตัวเลขทางการ

ผลรอบแรก: มีแผนและรายการตรวจ ยังไม่ถือว่าการย้ายหน้า/ข้อมูลผ่านการทดสอบหรือพร้อมใช้งานจริง ไม่มี runtime code, API, sheet หรือสิทธิ์ถูกแก้ในงานวางโครงสร้างนี้

## ตรวจรายละเอียดรอบสอง: จุดที่พบเพิ่มและแก้ในแผน

การตรวจรอบสองอ่านแผนเทียบโค้ดจริง ให้ผู้ตรวจอิสระตรวจแผนที่เขียนแล้ว และทดลองรวม CSV เดือนกันยายนด้วย decimal โดยไม่แก้ไฟล์ต้นทาง

### ข้อออกแบบที่ยังขวางการย้ายฟอร์มบันทึก

1. **Append revisions ยังไม่ใช่ atomic writer:** แผนตั้งต้นเสนอเก็บ revision ใหม่แต่ยังให้ CFO อ่านชีตเดิม หากไม่มี canonical store และ compatibility reader ชัดเจน ตัวเลขใหม่ไม่ถึง CFO หรือกลับไปต้อง clear/rewrite projection ซึ่งเสี่ยงเหมือนเดิม แผนฉบับปรับจึงระบุระยะ 5 ว่ายังติดข้อออกแบบ ต้องมี committed source, reader adapter, old-client rejection และ recovery ก่อนเปิด ไม่มีข้อสรุปว่าประวัติ revision เพียงอย่างเดียวแก้ concurrency แล้ว
2. **Overview กับรายละเอียดต้องใช้ report set เดียว:** แต่ละไฟล์อาจ export คนละเวลาแล้วตัวเลขถูกปรับย้อนหลัง การ publish ทีละไฟล์ทำให้หน้าแรกกับ drill-down ใช้คนละ revision ได้ เพิ่ม PublishedReportSet ซึ่งตรึง batch IDs, definition, coverage และผลกระทบยอด สลับ/ย้อนทั้งชุด ไฟล์ไม่ตรงยังแสดงได้เป็น “ยังไม่กระทบยอด” แต่ไม่อ้างว่าข้อมูลตรงกันแล้ว

### สัญญารายงานที่ทำให้ชัดขึ้น

- ค่าเงินเก็บ precision ของต้นฉบับ ไม่กำหนดว่า CSV ในอนาคตต้องละเอียดแค่สองตำแหน่ง แสดงสองตำแหน่งได้แต่ต้องกำหนด rounding/reconciliation tolerance ตามหลักฐาน
- เพิ่ม attribution metadata ในรายงานโฆษณา ไม่ใช่เฉพาะยอดขาย TikTok: window, click/view, event-date basis และ definition/version ถ้าไม่ทราบเก็บ unknown เดือนเดียวกันจึงยังไม่ใช่เหตุให้เทียบ ROAS ข้ามแพลตฟอร์มตรง ๆ
- ROAS รวมใช้ SUM ยอดขายให้เครดิต / SUM ค่าแอดของฐานที่ตรงกัน ห้ามเฉลี่ย ROAS ของแต่ละแถว ตัวหารศูนย์หรือข้อมูลขาดแสดง unavailable
- กำหนด selector ผลรวมชัดเจน: overview ใช้ standalone product + group root; product ใช้ standalone product + group member ไม่เอาสองชั้นมาบวกกัน และไม่ dedup product ID ซึ่งอาจลงหลายแคมเปญจริง
- เพิ่ม version ของ item-to-product mapping เพื่อไม่ให้เปลี่ยนทะเบียนปัจจุบันแล้วรายงานย้อนหลังเปลี่ยนตามโดยไม่แจ้ง
- ช่วงวันที่ครบเดือน, ประเภทโฆษณาครบ, ร้านครบ และข้อมูลออเดอร์ครบเป็นคนละสถานะ การมีออเดอร์สุดท้ายถึงสิ้นเดือนไม่ได้พิสูจน์ completeness
- ข้อกำหนด read-only หมายถึงไม่เพิ่ม import/manual mutation และไม่สร้างชีตจาก read ใหม่ ต้อง audit legacy GET ที่มี ensureSheet ด้วย ไม่อ้างว่า GET เดิมทุกตัวไม่มี side effect
