### กติกาของตัวทดลอง

- ข้อมูลย้ายครั้งแรกใช้รหัส snapshot + เลขแถวเป็นรหัสประวัติถาวร พร้อมต้นฉบับและ legacy key
- ข้อมูลอัปเดตใช้ business/platform/order ID และ item ID หากมี; L ตามด้วยตัวเลขถือเป็นรหัสสังเคราะห์ของระบบเดิมอย่างระมัดระวัง
- ถ้าไม่มี item ID ใช้ SKU จากแพลตฟอร์ม + ชื่อสินค้า + variation จับคู่เฉพาะกรณีที่มีคำตอบเดียว ไม่ใช้ master SKU, ยอดเงิน, สถานะ หรืออันดับใน batch เป็นตัวระบุ
- ถ้าออเดอร์เดิมมีสินค้าที่จับคู่ไม่ได้ จะหยุดให้ตรวจว่าเป็นสินค้าเพิ่มหรือเปลี่ยนชื่อ ไม่เพิ่มยอดอัตโนมัติ
- รวบรวมไฟล์ให้ครบก่อนตรวจและบันทึกด้วย transaction เดียว โค้ดนี้ยังไม่ใช่ HTTP endpoint การเชื่อม Upload ต้องมีที่พักข้อมูลแต่ละ chunk และคำสั่ง finalize ที่ยืนยันว่าครบไฟล์
- ย้อนกลับได้เฉพาะล็อตล่าสุดที่ยังมีผล และไม่ให้ย้อนลบ bootstrap; เก็บประวัติการแก้ไขไว้ ล็อตที่ย้อนแล้วต้องมีกระบวนการ replay ชัดเจนก่อนนำกลับมาใช้
- สูตรตัดสถานะเหมือนรุ่นแรก ยังไม่ได้เปลี่ยนนิยามยอดขาย

## โครงสร้างฐานทดลอง

snapshots เก็บที่มาและ hash ของ snapshot; source_rows เก็บต้นฉบับทุกแถวตามเลขแถว; orders เก็บข้อมูลที่พร้อมค้นและยอดเป็นสตางค์จำนวนเต็ม; quarantine เก็บเหตุผลที่ต้องตรวจ; order_history เก็บก่อนและหลังแก้ไข

คีย์ข้อมูลหลักใช้ business + platform + order_key เพื่อแยกธุรกิจ มีดัชนีวันที่/ช่องทางและ SKU/วันที่ รหัสออเดอร์เก็บเป็นข้อความ การนำเข้าแต่ละชุดใช้ transaction

ฐานทดลองเก็บทั้งสำเนาต้นฉบับและ payload สำหรับตรวจย้อนกลับ ขนาดรวม 113,860,608 bytes (ประมาณ 113.9 MB แบบ decimal) เป็นขนาดของฐานทดลองนี้ ไม่ใช่ขนาดขั้นต่ำของ orders และไม่รวมไฟล์สำรอง หากคงรูปแบบนี้และปริมาณต่อแถวใกล้กัน ข้อมูลใหม่ 704,000 แถวจะใช้ประมาณ 2.0 GB ก่อนเผื่อประวัติและข้อมูลระบบอื่น ต้องวัดโครงสร้างที่จะใช้งานจริงอีกครั้งก่อนรับรองโควตา Turso

## การทดสอบที่ผ่าน

- ชุดทดสอบ: นำเข้าซ้ำไม่เพิ่มแถว เปลี่ยนยอด/สถานะได้ เก็บรหัสที่ดูเหมือน scientific notation เป็นข้อความ บันทึกประวัติ rollback ได้ แยกธุรกิจ และปฏิเสธวันที่ผิด
- ข้อมูลจริง: snapshot เก็บครบและยอดตรง นำเข้าแถวที่ไม่กำกวมซ้ำแล้วไม่สร้างแถวหรือประวัติเพิ่ม
- SQLite integrity_check ผ่าน และตรวจสำรองด้วยการเปิดฐานสำรองอ่านกลับ

นี่เป็นการทดสอบ normalized rows จาก Sheets ยังไม่ใช่การเปลี่ยนตัวอ่านไฟล์ Shopee/TikTok/Lazada หรือเชื่อมหน้า Import เดิมเข้าฐานใหม่ และยังไม่ได้ทดสอบการลบล็อต/คืนสถานะย้อนหลังของ production

## ลำดับงานถัดไป

1. เก็บรหัสแถวสำหรับการย้ายข้อมูลแยกจาก legacy order_key พร้อม mapping กลับ snapshot/เลขแถว เพื่อรักษาประวัติครบ โดยไม่ถือว่าเลขแถวหรือ SKU คือรหัสรายการสำหรับการอัปเดตในอนาคต
2. ทดสอบตัวนำเข้าแยกจาก production: ใช้รหัสรายการจาก marketplace หากมี; กรณีไม่มีต้องออกแบบการจับคู่ที่ไม่เปลี่ยนเมื่อแบ่ง batch หรือเรียงแถวใหม่ และแยกรายการที่กำกวมให้ตรวจ ห้ามใช้ยอด/สถานะเป็นตัวระบุ เพราะเปลี่ยนได้
3. ตรวจจำนวนแถว ยอดตามวัน/ช่องทาง/SKU การนำเข้าซ้ำ การอัปเดตสถานะ และการลบล็อต เทียบระบบเดิม ก่อนเชื่อมหน้า Import ทดลอง
4. ทำรายงานทดลองอ่านฐานใหม่ขนานกับ Sheets จนยอดตรง แล้วจึงเตรียมการเชื่อม Turso และสลับระบบพร้อมทางย้อนกลับ

สถานะตอนนี้ยังเป็นฐานทดลองเดิม 39,985 แถวหลักและ 4 แถวแยกตรวจ ไม่ได้แก้ข้อมูล production หรือสลับ Dashboard และยังไม่ถือว่าทดสอบตัวนำเข้าใหม่ผ่านแล้ว
